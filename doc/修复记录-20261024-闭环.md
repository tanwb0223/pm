## 一、核心结论：三类断点都补上了

| 断点类型 | 修复前 | 修复后 |
|---|---|---|
| **有发送无接收** | 站内消息只写 `notify_log` 就记 SUCCESS，收件人永远读不到 | 新增 `sys_message` 收件箱 + 4 个接口 + 顶栏铃铛未读红点 |
| **有状态无出口** | 报表作废后回不去；补填放行只能开不能看/撤；预警处置流水无人读 | 作废重填跳过补填期校验；放行台账可看可撤；预警详情抽屉含处置时间线 |
| **有异常无补偿** | 定时任务失败只 `logger.exception`；通知重试被 SKIPPED 堵死 | 新增 `sys_job_run` + `/api/system/jobs`；重试只查 FAILED |

## 二、P0 修复清单

### 1. 站内消息收件箱（最重要）

- 新增 `sys_message` 表（`models/system.py`）：`receiver_id / biz_type / biz_id / level / title / body / read_at`
- `NotifyService.deliver()` 对 `channel=INNER` 改为**落一条 SysMessage** 再记成功；标题正文复用 `_compose`
- 新增 `services/message_service.py` + `api/v1/message.py`：
  - `GET /api/messages`（分页、只看未读）
  - `GET /api/messages/unread-count`
  - `POST /api/messages/{id}/read`（越权 403）
  - `POST /api/messages/read-all`
- 前端新增 `pages/Message/index.tsx`（路由 `/messages`）+ `AppLayout` 顶栏铃铛 Badge（60 秒轮询）

**波及自动修复**：预警通知、行内催办、超时升级、每日摘要 —— 四条链路都走 `deliver()` / `push_message()`，收件箱一次到位。

### 2. 橙色预警补邮件

`alert_service._create_or_merge` 里 ORANGE 也发 EMAIL（受新参数 `notify.orange.email` 控制）。橙色占 11 条规则里的 6 条，此前完全没有真实触达。

### 3. 通知重试不再饥饿

`retry_pending()` 只查 `status == FAILED`（原来 `status != SUCCESS` 把 SKIPPED 也算进去，SKIPPED 的 `_attempts()` 恒为 0，前 100 条全被它占满，真 FAILED 永远轮不到）。

### 4. 每日摘要正文不再丢失

原实现把统计 JSON 塞进 `NotifyLog.error`，`deliver()` 一失败就用错误文案覆盖 `error`，重投出去的是「昨日新增：0 条」。
改为：正文直接拼好 → `push_message()` 落站内 + `deliver_digest()` 发邮件。收件人从「仅 SYS_ADMIN」扩到 `SYS_ADMIN + PROJECT_OWNER`。

实测输出：`当前待处置：24 条 / 红色预警：1 条`（真实数字）。

### 5. 每小时扫描不再误关 AL-03

`AlertService.scan(day, only_codes=...)` 支持按规则子集扫描；`job_hourly_scan` 只扫 `{"AL-06"}`，`_auto_close` 也只对 AL-06 生效。另加「当天快照未生成则跳过快照类规则」的双重保护。

### 6. 定时任务可观测

`_with_lock` 统一写 `SysJobRun`（job_id / started_at / finished_at / status / message），新增 `GET /api/system/jobs`（`system:config`）。失败时 message 存异常摘要。

### 7. 报表截止时间时区修正

`deadline_of()` 从 `tzinfo=UTC` 改为 `ZoneInfo("Asia/Shanghai")` 构造后 `.astimezone(UTC)`。

实测：日报 = 北京次日 00:00、周报 = 北京次周一 12:00、月报 = 北京第 3 个工作日 18:00。

### 8. 作废历史报表可重填

`submit()` 先判断 `existing.status == 'VOIDED'` → **跳过补填期校验**直接复活。另在 `void()` 时自动开一条覆盖该周期的 `ReportGrace(kind=BACKFILL)`（30 天有效期）双保险。

### 9. 全新部署补齐 `report:grant`

权限点清单从手写改为 `core/permissions.py` 的 `ALL_PERMISSIONS` + `PERMISSION_META` 统一生成（含启动自检），`init_seed_data()` 遍历生成，另加 `_ensure_permissions()` 给存量库补插。

实测：全新库 40 项权限、`report:grant` / `project:sub:close` 均存在、7 个角色权限数与矩阵一致。

### 10. 数据范围修复

- `apply_scope` 对 `ProjMajor` 特判：MAJOR 范围用 `id.in_(major_ids)`，COLLEGE 范围用参与学院子查询（原来命中 `where(false())`，列表恒空）
- `get_major()` 增加 `owner_id == user.id` 分支（SELF 范围的大项目负责人原来能列出却打不开详情）
- `GET /api/progress/major/{id}` 补 `require_perm("progress:table")` + 范围校验

### 11. 权限矩阵按需求附录二重排

| 角色 | 变化 |
|---|---|
| COLLEGE_OWNER | **补** `project:sub:edit`、`project:sub:close`、`progress:urge`、`export:*` |
| PROJECT_OWNER | **移除** `report:void`（需求 3.4：作废仅管理员） |
| SUB_OWNER | **补** `alert:close` |
| VIEWER | **补** `report`（需求 2.2：查看者能看报表） |
| REPORTER | **移除** export 系列（附录二：填报人导出=—） |

导出接口补 `require_perm("export:ledger"/"export:progress")`，`export:*` 不再是死权限点。
