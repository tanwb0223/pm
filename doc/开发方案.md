# 产教融合项目管理系统 · 开发方案

> 依据：`doc/产教融合项目管理系统-需求方案说明书-V1.4.docx`（42 项确认事项）
> 技术栈：**Python FastAPI + React 18 + TypeScript + Ant Design 5 + PostgreSQL**
> 编制日期：2026-10-19

---

## 一、总体结论（先看这 5 条）

1. **架构用单体应用**：一个 FastAPI 进程 + 一个 React 静态包 + PostgreSQL。不上微服务、不上 K8s、不上消息队列。子项目约 300 个、教师约 1000 人，这个体量上分布式只会增加排障成本。
2. **PostgreSQL 在这个项目上是加分项**：`generate_series`、窗口函数、`jsonb`、**advisory lock** 四样东西正好命中本系统的难点（连续 N 天判定、日历展开、报表动态字段、定时任务防重跑）。
3. **Ant Design 5 是本项目的正确选择**：表格、表单、树形选择、日期区间、中文文案全部开箱即用，能省掉 1–2 周的组件搭建期。代价是设计偏"标准后台"、有版本锁定。详见 2.4。
4. **真正的技术难点仍是三个**：预警引擎（11 条规则 + 免填期计时 + 去重）、双日历（自然日 vs 有效日）、数据范围权限（一人多角色、不同项目不同身份）。其余是常规 CRUD。
5. **系统范围已定：一期只管执行期（建档→结项），验收/经费/后评价在数据模型里预留字段，二期再启用。** 一期约 **288 人天（14.4 人月）**，3 人并行约 14 周；二期验收+后评价增量约 3 人月。详见第十章。

### 2.2 为什么这样选（关键几条）

**PostgreSQL 是本项目的正确选择**

| 需求 | PG 特性 |
|---|---|
| 连续 N 天偏差 < −10%（AL-01） | 窗口函数 + `GROUP BY ... HAVING COUNT(*)`，或 `generate_series` 补齐空日 |
| 免填日历展开 | `generate_series(date, date, '1 day')` 一行生成区间 |
| 报表三种类型的动态字段 | `jsonb` + GIN 索引，查询不用改表结构 |
| 定时任务多实例防重跑 | `pg_try_advisory_lock`，比引入 ShedLock/Redis 锁简单 |
| 周报/月报按周按月聚合 | `date_trunc('week', ...)` |

**FastAPI 的取舍**

- 优点：Pydantic 自动校验、OpenAPI 自动文档（可直接给校方当接口文档）、异步 IO。
- 代价：**没有 Spring Security 那种开箱即用的权限框架**，认证授权要自己搭（约 3–5 天）。
- 结论：仍然值得，因为业务逻辑以查询和计算为主，Python 写规则比 Java 快。

### 2.3 一个重要决策：SQLAlchemy 用同步还是异步

**建议用同步（`Session`，不用 `AsyncSession`）**，理由：

| | 同步 | 异步 |
|---|---|---|
| 并发能力 | 100 用户 + 连接池（20–40）完全够 | 更高，但本项目用不上 |
| 开发体验 | 简单，不会遇到 `MissingGreenlet` 这类坑 | 异步 session 生命周期、懒加载问题多 |
| 调试 | 堆栈清晰 | 堆栈绕 |
| 第三方库 | 全部兼容 | 部分库（如某些 PDF/Excel 库）是同步的，要 `run_in_threadpool` |

**做法**：Uvicorn 起 4 个 worker，每个 worker 一个连接池，同步 SQLAlchemy。总连接数 = 4 × 10 = 40，PG 默认 100 上限，够用。

> 如果后续真的有高并发场景（比如全校同时填报），再单独把几个热点接口改异步，不用整体重构。

### 2.4 Ant Design 5 的取舍（改用 antd 后的变化）

选 antd 后，原来需要自己搭的基础设施**全部开箱即用**：

| 能力 | antd 提供 | 本项目怎么用 |
|---|---|---|
| 数据表格 | `Table` 内置分页/排序/筛选/固定列/行选择 | 进度总表直接用，只需接服务端分页参数 |
| 表单 | `Form` + 内置校验规则 | 项目建档、报表填报 |
| 树形选择 | `TreeSelect` | 选学院、选项目 |
| 日期区间 | `DatePicker.RangePicker` | 计划起止时间、筛选区间 |
| 弹窗表单 | `Modal` + `Form` | 新增/编辑统一用 |
| 消息提示 | `message` / `notification` | 全局提示 |
| 中文 | `ConfigProvider locale={zhCN}` | 一行配置 |
| 主题 | `ConfigProvider theme={{ token }}` | 改主色即可 |

**代价（需要接受）**：

| 项 | 说明 |
|---|---|
| 视觉风格 | 偏"标准后台"，不像 shadcn/ui 那么有设计感。高校管理系统这个风格反而合适 |
| 包体积 | 全量约 400KB+ gzip，可用按需加载优化；内网系统影响不大 |
| 版本锁定 | 大版本升级有破坏性变更；本项目周期短，问题不大 |
| 深度定制 | 想大改样式要覆盖 CSS，不如 Tailwind 自由 |

**结论**：对这类"表单 + 表格 + 图表"为主的管理系统，**antd 是更务实的选择**，能省 1–2 周。M0 基础搭建期从 2 周缩回 **1 周**。

**仍然建议封装的 3 个薄封装**（不是重造组件，只是统一约定）：
1. `ProTable`（包一层 antd Table，统一分页参数、请求封装、导出按钮、列显隐记忆）
2. `ProgressCell`（进度条 + 偏差颜色 + "数据可信度"灰显标记，对应文档 3.2(7)）
3. `AlertBadge`（预警等级徽标 + 计数，红色/橙色/黄色统一色值）

### 2.5 明确不用的技术

| 不用 | 原因 |
|---|---|
| Tailwind CSS | antd 已提供完整样式体系，两套混用会增加冲突和心智负担 |
| shadcn/ui | 见 2.4，本项目表格表单密集，antd 更省时 |
| Celery | 需要 Redis/RabbitMQ broker + worker 进程，本项目定时任务量很小，APScheduler 够 |
| Django | 自带 Admin/ORM 很方便，但 FastAPI 已定；且 Django 的同步范式在 API 场景不如 FastAPI 灵活 |
| 微服务 / K8s | 体量不匹配 |
| MongoDB | 强关系型业务，PG 的 `jsonb` 已能覆盖动态字段 |
| 工作流引擎 | 方案明确"不设审批环节" |
| GraphQL | REST 够用，OpenAPI 文档对交付更友好 |

## 四、数据模型（PostgreSQL）

### 4.1 建表约定

| 项 | 约定 |
|---|---|
| 主键 | `bigint GENERATED ALWAYS AS IDENTITY`（比 serial 规范） |
| 时间 | `timestamptz`（带时区），统一存 UTC |
| 日期 | `date`（无时区，如计划起止日、免填日） |
| 枚举 | **用 `varchar` + `CHECK` 约束**，不用 PG 原生 enum（原生 enum 改值很麻烦） |
| 软删除 | 项目类表用 `deleted_at timestamptz`；流水类表不删 |
| 审计字段 | `created_at`、`created_by`、`updated_at`、`updated_by` |
| 命名 | 表名蛇形复数，字段蛇形 |

### 4.2 核心表（20 张）

#### 组织与权限（6 张）

```sql
-- 人员
CREATE TABLE sys_user (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    staff_no      varchar(32) NOT NULL UNIQUE,      -- 工号
    name          varchar(64) NOT NULL,
    college_id    bigint REFERENCES sys_college(id),
    phone         varchar(20),
    email         varchar(128),
    password_hash varchar(255),
    status        varchar(16) NOT NULL DEFAULT 'ACTIVE'
                  CHECK (status IN ('ACTIVE','DISABLED')),
    last_login_at timestamptz,
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now()
);

-- 学院
CREATE TABLE sys_college (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name      varchar(128) NOT NULL,
    code      varchar(32) UNIQUE,
    parent_id bigint REFERENCES sys_college(id)
);

-- 角色
CREATE TABLE sys_role (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code      varchar(64) NOT NULL UNIQUE,
    name      varchar(64) NOT NULL,
    is_system boolean NOT NULL DEFAULT false,
    remark    varchar(255)
);

-- ★ 授权：一人多角色 + 不同项目不同身份
CREATE TABLE sys_user_role (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    bigint NOT NULL REFERENCES sys_user(id),
    role_id    bigint NOT NULL REFERENCES sys_role(id),
    scope_type varchar(16) NOT NULL
               CHECK (scope_type IN ('ALL','MAJOR','COLLEGE','SELF','CUSTOM')),
    scope_id   bigint,           -- MAJOR→大项目id；COLLEGE→学院id；其余为 NULL
    valid_from date,
    valid_to   date,             -- 自定义授权默认 1 学期
    created_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (user_id, role_id, scope_type, scope_id)
);
CREATE INDEX idx_user_role_user ON sys_user_role(user_id);

-- 权限点（模块—页面—操作 三级）
CREATE TABLE sys_permission (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code      varchar(128) NOT NULL UNIQUE,   -- project:sub:edit
    name      varchar(64) NOT NULL,
    type      varchar(16) NOT NULL CHECK (type IN ('MODULE','PAGE','ACTION')),
    parent_id bigint REFERENCES sys_permission(id),
    sort      int NOT NULL DEFAULT 0
);

CREATE TABLE sys_role_permission (
    role_id       bigint NOT NULL REFERENCES sys_role(id),
    permission_id bigint NOT NULL REFERENCES sys_permission(id),
    PRIMARY KEY (role_id, permission_id)
);
```

> **`sys_user_role` 是整套权限的地基**。同一位老师可以在 A 项目里是"学院负责人"、在 B 项目里是"填报人"，靠 `(role_id, scope_type, scope_id)` 三元组表达。

#### 项目与进度（5 张）

```sql
CREATE TABLE proj_major (
    id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name           varchar(255) NOT NULL,
    type           varchar(32) NOT NULL,          -- 产业学院/实训基地/订单班/课程教材/双师基地
    partner_company varchar(255),
    build_period   varchar(64),
    owner_id       bigint REFERENCES sys_user(id),
    status         varchar(16) NOT NULL DEFAULT 'ACTIVE'
                   CHECK (status IN ('ACTIVE','CLOSED','ABORTED')),
    -- ★ 第 38 项：原始计划（立项时锁定，不随变更改动）
    original_start date,
    original_end   date,
    -- ★ 第 32 项预留：验收相关字段。一期只存不用，二期直接启用，不改表
    acceptance_status varchar(16) DEFAULT 'NOT_REQUIRED'
                      CHECK (acceptance_status IN ('NOT_REQUIRED','PENDING','PASSED','RECTIFYING','REJECTED')),
    acceptance_date   date,
    acceptance_org    varchar(128),
    -- ★ 第 34 项预留：经费
    budget_total      numeric(14,2),
    budget_used       numeric(14,2),
    -- ★ 第 42 项预留：后评价
    evaluation_score  numeric(5,2),
    evaluation_note   jsonb,
    incomplete_reason jsonb,      -- 完整性检查结果缓存
    created_at     timestamptz NOT NULL DEFAULT now(),
    deleted_at     timestamptz
);

-- 大项目 ↔ 学院（多对多）
CREATE TABLE proj_major_college (
    major_id         bigint NOT NULL REFERENCES proj_major(id),
    college_id       bigint NOT NULL REFERENCES sys_college(id),
    college_owner_id bigint REFERENCES sys_user(id),
    PRIMARY KEY (major_id, college_id)
);

-- ★ 子项目：major_id 和 college_id 都必须非空
CREATE TABLE proj_sub (
    id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    major_id         bigint NOT NULL REFERENCES proj_major(id),
    college_id       bigint NOT NULL REFERENCES sys_college(id),
    name             varchar(255) NOT NULL,
    owner_id         bigint REFERENCES sys_user(id),
    plan_start       date,
    plan_end         date,
    -- ★ 第 38 项：子项目级原始计划（用于算"比原计划晚多少天"）
    original_start   date,
    original_end     date,
    weight           numeric(8,2),          -- 可空，空则等权
    status           varchar(16) NOT NULL DEFAULT 'NOT_STARTED'
                     CHECK (status IN ('NOT_STARTED','IN_PROGRESS','ABORTED','CLOSED')),
    current_progress int NOT NULL DEFAULT 0 CHECK (current_progress BETWEEN 0 AND 100),
    last_update_at   timestamptz,
    closed_at        timestamptz,
    -- ★ 第 32 项预留：结项后的验收状态（一期恒为 NOT_REQUIRED）
    acceptance_status varchar(16) DEFAULT 'NOT_REQUIRED'
                      CHECK (acceptance_status IN ('NOT_REQUIRED','PENDING','PASSED','RECTIFYING','REJECTED')),
    created_at       timestamptz NOT NULL DEFAULT now(),
    deleted_at       timestamptz
);
CREATE INDEX idx_sub_major   ON proj_sub(major_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_sub_college ON proj_sub(college_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_sub_owner   ON proj_sub(owner_id) WHERE deleted_at IS NULL;
```

### 5.2 进度与汇总（M2）

**① 时间进度公式**（文档 4.2，自然日）

```python
def time_progress(plan_start: date, plan_end: date, today: date) -> int:
    if today < plan_start:
        return 0
    if today >= plan_end:
        return 100
    total = (plan_end - plan_start).days
    if total <= 0:
        return 100
    passed = (today - plan_start).days
    return max(0, min(100, passed * 100 // total))
```

**② 汇总**（文档 4.1 + 第 20、21 项）

```python
def aggregate_major(major_id: int, today: date) -> int:
    subs = get_active_subs(major_id)   # 只取 IN_PROGRESS + CLOSED
    if not subs:
        return 0
    # 权重：未设定按等权；Σ权重=0 退化为等权
    weights = [s.weight or Decimal(1) for s in subs]
    total_w = sum(weights)
    if total_w == 0:
        weights = [Decimal(1)] * len(subs)
        total_w = Decimal(len(subs))
    # 已结项按 100% 计入
    values = [100 if s.status == 'CLOSED' else s.current_progress for s in subs]
    return int(sum(v * w for v, w in zip(values, weights)) / total_w)
```

- 学院进度：该学院在该大项目内子项目加权
- 全校进度：各大项目等权平均（一期，界面注明）

**③ 数据量小，实时算即可**，不做物化视图。

#### 5.3.3 "连续 N 天"用快照 + 纯 SQL

AL-01 要求"偏差 < −10% 且持续 3 个自然日以上"：

```sql
-- 连续 3 个有效日偏差都 < -10%
SELECT sub_id
FROM prog_snapshot
WHERE snap_date BETWEEN %(start)s AND %(end)s
  AND deviation < -10
  AND is_free_day = false
GROUP BY sub_id
HAVING COUNT(*) >= 3;
```

同理：
- AL-03 停滞：`days_since_update >= 21`（按有效日计）
- AL-11 长期零进度：连续 60 个有效日 `actual_progress = 0`
- AL-02 严重滞后：当日 `deviation <= -25`（建议加 1 天防抖）

**好处**：规则全是 SQL，可追溯、可重跑、可解释。管理者问"为什么报我"，能拿出快照数据。

#### 5.3.4 双日历（**关键设计决策**）

文档里有两套时间口径，**必须分开实现**：

| 用途 | 口径 | 依据 |
|---|---|---|
| 时间进度公式 | **自然日**，含当日 | 4.2 明确"按自然日计算" |
| 预警计时（停滞/零进度/滞后持续） | **有效日**，排除免填期 | 4.2"免填期内三项计时暂停，恢复后顺延" |

```python
class CalendarService:
    def __init__(self):
        self._free_days: set[date] = set()   # 启动时加载全年

    def is_free_day(self, d: date) -> bool:
        return d in self._free_days

    def natural_days_between(self, a: date, b: date) -> int:
        return (b - a).days

    def effective_days_between(self, a: date, b: date) -> int:
        """排除免填日"""
        if b <= a:
            return 0
        total = (b - a).days
        free = sum(1 for d in self._iter_days(a, b) if d in self._free_days)
        return total - free
```

**性能**：免填日一年几百条，启动加载进内存（`set`），不查库。日期变更时用 Redis pub/sub 或简单的缓存失效通知。

> ⚠️ **这是最需要确认的技术细节**：文档说"免填期内偏差值仍展示但不触发预警"，那么"滞后持续 3 天"是"连续 3 个有效日"还是"连续 3 个自然日、其中免填日跳过"？跨寒假时两种算法结果不同。**我默认按有效日连续 3 天实现**（更符合"计时暂停"的本意）。

```python
def run_with_lock(func):
```

```python
def apply_scope(query, user: User, model):
    scopes = user.scopes   # 从 sys_user_role 加载
    if any(s.type == 'ALL' for s in scopes):
        return query
    conds = []
    for s in scopes:
        if s.type == 'MAJOR':
            conds.append(model.major_id == s.scope_id)
        elif s.type == 'COLLEGE':
            conds.append(model.college_id == s.scope_id)
        elif s.type == 'SELF':
            conds.append(or_(model.owner_id == user.id, model.id.in_(user.granted_sub_ids)))
    return query.filter(or_(*conds)) if conds else query.filter(false())
```

```sql
-- 进度更新及时率（14 天口径）
WITH stat_period AS (
    SELECT %(start)s::date AS d_start, %(end)s::date AS d_end
),
should_update AS (
    SELECT s.id FROM proj_sub s, stat_period p
    WHERE s.status = 'IN_PROGRESS'
      AND s.plan_start <= p.d_end AND s.plan_end >= p.d_start
),
updated AS (
    SELECT DISTINCT r.sub_id FROM prog_record r, stat_period p
    WHERE r.created_at::date BETWEEN p.d_start AND p.d_end
    GROUP BY r.sub_id
    HAVING COUNT(DISTINCT date_trunc('week', r.created_at)) * 14 >= (p.d_end - p.d_start)
)
SELECT COUNT(u.sub_id)::numeric / NULLIF(COUNT(su.id), 0) FROM should_update su
LEFT JOIN updated u ON u.sub_id = su.id;
```

## 九、需要你确认的事项

### 9.0 Q1 到底在问什么（重要，先看这段）

**Q1 就是需求文档 6.3 的第 32 项**："系统管到哪一步：只管执行期，还是管到验收和后评价"。

用大白话说，就是**这个系统从项目生命的哪个点开始管、到哪个点结束**。项目一般分四段：

```
① 申报立项        ② 建设执行        ③ 验收          ④ 后评价
申报→评审→批复    分解任务→填报进度   学校/上级验收    效果评估
                  →预警督办→结项     →整改→复验      →成果沉淀
     ↑                  ↑                  ↑               ↑
   不在系统内      ← 系统管这一段 →     ? 管不管？      ? 管不管？
```

**现状（文档 V1.4 的定位）**：只做 ②，也就是"立项建档 → 任务分解 → 过程填报 → 偏差识别 → 预警督办 → 汇总导出 → 结项归档"（文档 2.4 节的七步闭环）。① 在 OA 走，系统只接收已批项目。

**第 32 项问的是**：③ 验收 和 ④ 后评价 要不要也做进系统？

**两种答案的差别**：

| | 方案 A：只管执行期（默认） | 方案 B：管到验收和后评价 |
|---|---|---|
| 结项之后 | 子项目变只读，结束 | 还能记录验收结论、整改事项、复验结果 |
| 新增功能 | 无 | 验收记录、整改跟踪、成效登记表、后评价指标 |
| 新增表 | 无 | 3–4 张（验收单、整改项、成效指标、评价结果） |
| 新增页面 | 无 | 3–4 个 |
| **工作量** | 基准 | **+2–3 人月（约 +4–6 周）** |
| 适用场景 | 学校只想要"过程看得见、问题有人管" | 学校要拿系统当"项目全生命周期档案"，应付上级检查 |

**为什么这条必须先定**：

1. **它决定结项是不是终点**。如果选 B，"结项"只是中间状态，后面还有验收、整改、复验，数据模型和状态机都要改。
2. **它决定系统是不是"项目档案"**。选 A 的系统，项目做完就归档了，翻不出"验收结论是什么""整改完了没有"。而学校迎接检查时，恰恰要这些。
3. **改起来很贵**。如果先按 A 做完再改 B，`proj_sub` 的状态机、结项逻辑、权限、报表都要动，返工成本比一开始就做高得多。

**结论（已采纳，本方案按此执行）**：

> **一期选方案 A（只管执行期），但在数据模型里预留验收、经费、后评价字段。**
>
> 理由：
> 1. 一期工期和预算可控，先跑通"建档 → 填报 → 预警"这个核心闭环，价值最高；
> 2. 预留字段的成本几乎为零（多 6 个可空字段），但二期加功能时**不用改表、不用迁移数据**；
> 3. 结项后的验收、整改、后评价做成二期增量，届时按学校实际检查要求设计，比现在拍脑袋更准。

**已预留的字段**（见 4.2 建表 SQL）：

| 表 | 预留字段 | 对应确认项 |
|---|---|---|
| `proj_major` | `acceptance_status`、`acceptance_date`、`acceptance_org` | 第 32、33 项（验收） |
| `proj_major` | `budget_total`、`budget_used` | 第 34 项（经费） |
| `proj_major` | `evaluation_score`、`evaluation_note` | 第 42 项（后评价） |
| `proj_major` / `proj_sub` | `original_start`、`original_end` | 第 38 项（原始计划） |
| `proj_sub` | `acceptance_status` | 第 32、33 项（子项目验收） |

一期这些字段**只建不用**，默认值 `NOT_REQUIRED`，界面不展示。

**一句话问校方**：
> "项目结项之后，学校还需要在系统里记录验收结论、整改情况和最终成效吗？还是结项后这个项目就不用在系统里管了？"
