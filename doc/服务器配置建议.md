# 服务器配置建议

数据库与应用部署在同一台服务器时的配置方案。

---

## 一、结论先行

按需求文档的规模（1000 名教师、300 个子项目、50 个大项目），**数据库和应用同机部署完全可行**，推荐配置：

| 场景 | CPU | 内存 | 磁盘 | 说明 |
|---|---|---|---|---|
| **最低可用** | 2 核 | 4 GB | 100 GB SSD | 能跑，但无余量，不推荐生产 |
| **推荐配置** | **4 核** | **8 GB** | **200 GB SSD** | 生产首选，有余量应对峰值 |
| 宽裕配置 | 8 核 | 16 GB | 500 GB SSD | 附件多、或要跑多个系统时 |

**关键约束**：磁盘必须是 **SSD**，不要用机械硬盘。PostgreSQL 对随机 IO 敏感，机械盘下进度总表的聚合查询会明显变慢。

---

## 二、为什么是这个配置

### 2.1 内存分配

同机部署时，内存要分给三方：

```
总内存 8 GB
├── PostgreSQL        2.5 GB   （shared_buffers 2GB + 系统缓存）
├── 应用（uvicorn）   1.5 GB   （2 worker × 约 300MB + 余量）
├── 操作系统          1.0 GB
└── 峰值余量          3.0 GB   （并发填报、导出大文件时）
```

**PostgreSQL 是最耗内存的**，但不是越多越好：

| 总内存 | shared_buffers 建议 | 说明 |
|---|---|---|
| 4 GB | 1 GB | 最低，勉强够用 |
| 8 GB | **2 GB** | 推荐，PostgreSQL 官方建议为总内存 25% |
| 16 GB | 4 GB | 宽裕 |

> `shared_buffers` 不要超过总内存的 40%，否则会和文件系统缓存抢内存，反而变慢。

**应用侧内存**：uvicorn 每个 worker 约 250-350MB（SQLAlchemy + FastAPI + 依赖）。配置 `--workers 2` 时约 700MB，留足余量按 1.5GB 计。

### 2.2 CPU

| 负载 | 说明 |
|---|---|
| 日常 | 1000 名教师分散填报，平均并发约 10-20 请求/秒，2 核足够 |
| 峰值 | 每周一上午 8:30-10:00 集中填周报，可能瞬时 50-80 请求/秒 |
| 定时任务 | 每日 01:00 生成快照（300 条 INSERT）+ 预警扫描，约 3-5 秒，占 1 核 |

4 核的意义在于：**峰值时不会因为一个慢查询拖死整个系统**。

### 2.3 磁盘

分三部分：

| 用途 | 3 年预估 | 说明 |
|---|---|---|
| 数据库 | **约 14 GB** | 含索引与膨胀余量（见下方测算） |
| 附件 | **约 9 GB** | 按每子项目每年 5 个附件、平均 2MB |
| 备份 | **约 5 GB** | pg_dump 压缩后，保留 30 天 |
| 系统与程序 | 约 10 GB | 操作系统 + 程序与虚拟环境（约 800MB）+ 日志 |
| **合计** | **约 38 GB** | 200 GB 有 5 倍余量，足够 |

**数据库体积测算明细**（1000 教师 / 300 子项目 / 3 年）：

| 表 | 3 年行数 | 体积 | 说明 |
|---|---|---|---|
| `prog_snapshot` | 328,500 | 38 MB | 每日快照，行数最多但单行小 |
| `report` | 46,800 | 91 MB | 报表含正文，单行 2KB |
| `audit_log` | 200,000 | 98 MB | 保留 2 年，单行 0.5KB |
| `prog_record` | 46,800 | 9 MB | 进度留痕 |
| `alert` | 10,800 | 5 MB | 预警 |
| 其他 22 张表 | — | < 5 MB | 组织、用户、角色、参数等 |
| **合计** | — | **约 250 MB** | |

> **注意**：上表是纯数据量。加上主键索引、外键索引、TOAST、页面膨胀，实际占用约为数据的 1.5-2 倍，即 **约 500 MB**。
>
> 之前的 14 GB 估算是按更激进的假设（每子项目每周填报、报表正文更长）算的上限。**实际 3 年大概率在 1-3 GB 区间**，200 GB 磁盘绰绰有余。

## 三、PostgreSQL 参数调优

同机部署时，PostgreSQL 需要限制资源占用，避免和应用抢内存。

编辑 `postgresql.conf`（位置：`/etc/postgresql/18/main/postgresql.conf`）：

```ini
# ============================================================
# 内存（按 8GB 总内存配置）
# ============================================================
shared_buffers = 2GB              # 总内存 25%
effective_cache_size = 5GB        # 总内存 60%，告诉优化器有多少可用缓存
work_mem = 16MB                   # 单查询排序/哈希内存，4 核可同时跑 4 个
maintenance_work_mem = 256MB      # 维护操作（VACUUM、建索引）

# ============================================================
# 连接（与应用连接池匹配）
# ============================================================
max_connections = 100             # 应用 pool_size=10 + max_overflow=20，2 worker = 最多 60
                                  # 留 40 给运维连接、备份

# ============================================================
# 写入性能（SSD 可放宽）
# ============================================================
wal_buffers = 16MB
checkpoint_completion_target = 0.9
max_wal_size = 2GB
min_wal_size = 512MB

# ============================================================
# 查询规划
# ============================================================
random_page_cost = 1.1            # SSD 随机读接近顺序读（机械盘用 4.0）
effective_io_concurrency = 200    # SSD 并发 IO 能力强

# ============================================================
# 日志（排查慢查询）
# ============================================================
log_min_duration_statement = 1000 # 记录超过 1 秒的查询
log_checkpoints = on
log_connections = off             # 连接频繁，开了日志会很大
log_disconnections = off
```

### 关键参数说明

**`max_connections = 100` 与连接池的配合**：

应用侧 `pool_size=10, max_overflow=20`，每个 worker 最多 30 个连接：

```
2 worker × 30 = 60 个应用连接
+ 运维/备份/监控 约 10 个
= 70，max_connections=100 有 30 个余量
```

如果启动更多 worker（如 4 个），要相应调大 `max_connections` 到 150，或减小 `pool_size`。

**`random_page_cost = 1.1`**：这个参数对性能影响很大。默认值 4.0 是给机械硬盘的，SSD 上用 1.1 能让优化器更愿意走索引。

## 四、同机部署的配置要点

### 4.1 服务启动参数

应用通过 systemd 管理，关键是 worker 数与内存：

```ini
[Service]
WorkingDirectory=/opt/pm/backend
ExecStart=/opt/pm/backend/.venv/bin/uvicorn app.main:app \
    --host 0.0.0.0 \
    --port 8000 \
    --workers 2 \
    --proxy-headers \
    --forwarded-allow-ips='*'
```

`--workers 2` 时每个 worker 约 300MB，合计约 600MB，加上 Python 基础开销按 1.5GB 预留。

### 4.2 PostgreSQL 共享内存

PostgreSQL 做并行查询、大排序时用共享内存。如果 `/dev/shm` 太小（部分虚拟化环境默认 64MB），会报错：

```
ERROR: could not resize shared memory segment
```

检查：

```bash
df -h /dev/shm
```

小于 256MB 时，编辑 `/etc/fstab` 增大：

```
tmpfs /dev/shm tmpfs defaults,size=512M 0 0
```

然后 `sudo mount -o remount /dev/shm`。

### 4.3 端口收口

数据库**只监听本机**，不对外暴露：

```bash
# /etc/postgresql/18/main/postgresql.conf
listen_addresses = 'localhost'
```

应用通过 `127.0.0.1:5432` 访问，外部无法直连。这样即使防火墙配置有误，数据库也不会暴露。

本地连库调试：

```bash
sudo -u postgres psql -d pm_prod
```

## 五、同机部署的注意事项

### 5.1 端口只开一个

数据库端口**不要**映射到宿主机：

```yaml
db:
  # ports:
  #   - "5432:5432"      # 生产环境不要开
```

应用通过 `127.0.0.1:5432` 访问，外部无法直连数据库。这样即使防火墙配置有误，数据库也不会暴露。

需要本地连库调试时，临时用：

```bash
sudo -u postgres psql -d pm_prod
```

### 5.2 备份与应用错峰

应用侧定时任务：01:00 生成快照 + 预警扫描。
备份任务应避开这个时段，建议 **02:00**：

```cron
0 2 * * * /opt/pm/backup.sh >> /data/pm/log/backup.log 2>&1
```

同时备份时 `pg_dump` 会占用 IO，建议限制优先级：

```bash
nice -n 19 ionice -c 3 pg_dump ...
```

### 5.3 内存不足的表现

如果配置偏低，最先出现的症状是：

| 症状 | 原因 | 处理 |
|---|---|---|
| 查询突然变慢 10 倍 | `shared_buffers` 太小，频繁读磁盘 | 调大 `shared_buffers` |
| OOM Killer 杀掉进程 | 应用 + PG 总内存超限 | 降低 `shared_buffers` 或加内存 |
| `could not resize shared memory` | `/dev/shm` 太小 | 设 `shm_size: 256mb` |
| 连接数报错 | `max_connections` 不够 | 调大或减 worker 数 |

查看 OOM 记录：

```bash
dmesg | grep -i "out of memory"
```

### 5.4 定时任务的多实例安全

应用内置的 APScheduler 用 **PostgreSQL advisory lock** 去重，即使启动多个 worker 或多个容器副本，任务也只会执行一次。

所以同机部署时不需要额外的任务调度服务。

## 六、不同规模对应的配置

如果学校规模与需求文档假设不同，按下表调整：

| 教师数 | 子项目数 | CPU | 内存 | 磁盘 | shared_buffers |
|---|---|---|---|---|---|
| 500 | 100 | 2 核 | 4 GB | 100 GB | 1 GB |
| **1000** | **300** | **4 核** | **8 GB** | **200 GB** | **2 GB** |
| 2000 | 600 | 4 核 | 16 GB | 300 GB | 4 GB |
| 3000+ | 1000+ | 8 核 | 16 GB | 500 GB | 4 GB |

**判断依据**：
- 每 500 名教师 + 150 个子项目，约需 1 核 + 2GB 内存
- 磁盘按每子项目每年 30MB 估算（含附件）
- 超过 2000 名教师时，建议把数据库单独放到一台机器

## 七、部署检查清单

同机部署前确认：

- [ ] 磁盘是 SSD（`lsblk -d -o name,rota` 显示 `0` 为 SSD）
- [ ] 内存 ≥ 8GB（`free -h`）
- [ ] `shared_buffers` 设为总内存 25%
- [ ] `shm_size` 设为 256MB 以上
- [ ] 数据库端口未映射到宿主机
- [ ] 备份时间与应用定时任务错峰
- [ ] 防火墙只开 80/443（或 8000）
- [ ] 交换分区（swap）设为内存的 1-2 倍，作为 OOM 兜底
- [ ] 配置 `log_min_duration_statement` 便于排查慢查询

### 关于 swap

同机部署时建议开 swap，虽然会变慢，但能避免进程被 OOM Killer 直接杀掉：

```bash
sudo fallocate -l 8G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

调整使用倾向（越小越不愿意用 swap）：

```bash
sudo sysctl vm.swappiness=10
```

## 八、监控建议

同机部署时资源竞争是主要风险，建议监控：

```bash
# 实时看资源占用
top -b -n 1 | head -20
ps aux --sort=-%mem | head -10

# 看 PostgreSQL 慢查询
sudo -u postgres psql -d pm_prod \
  -c "SELECT query, mean_exec_time, calls FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;"
```

需要开启 `pg_stat_statements` 扩展（在 `postgresql.conf` 的 `shared_preload_libraries` 中加入）。

简单的资源告警脚本：

```bash
#!/bin/bash
# 内存使用超 90% 告警
MEM=$(free | awk '/Mem:/ {printf "%.0f", $3/$2*100}')
if [ "$MEM" -gt 90 ]; then
    echo "内存使用 ${MEM}%，请检查" | mail -s "PM系统内存告警" admin@school.edu.cn
fi

# 磁盘使用超 85% 告警
DISK=$(df /data | awk 'NR==2 {print $5}' | tr -d '%')
if [ "$DISK" -gt 85 ]; then
    echo "磁盘使用 ${DISK}%，请清理" | mail -s "PM系统磁盘告警" admin@school.edu.cn
fi
```

## 九、总结

**同机部署是可以的**，关键在于：

1. **内存要够**：8GB 是舒适线，4GB 是底线
2. **磁盘要 SSD**：这是性能的分水岭
3. **PostgreSQL 要限内存**：`shared_buffers` 占总内存 25%，不能让它无限增长
4. **端口要收口**：数据库只监听 127.0.0.1，不对外暴露
5. **备份要错峰**：避开 01:00 的定时任务

如果学校机房能给到 **4 核 8GB + 200GB SSD**，这套系统可以稳定跑 3-5 年不需要升级。
