# 产教融合项目管理系统 · 代码分析报告

> 分析时间：2026-10-21　范围：`backend/app` + `frontend/src`　基线：`50eeb61`（含未提交改动）
> 方法：静态阅读 + 运行时实测（SQLite 现有库 `D:/data/pm/pm.db`、FastAPI 路由表反射、SQL 计数）

## 一、总体评价

| 维度 | 数据 |
|---|---|
| 后端 | 11,014 行 Python，103 个接口，23 张表，5 个 Alembic 迁移 |
| 前端 | 9,813 行 TS/TSX，22 个页面 + 7 个组件，构建产物 2.2 MB（antd / echarts / react 已分 chunk） |
| 数据层 | SQLAlchemy 2.1 同步 ORM，SQLite（默认）与 PostgreSQL 双支持 |
| 质量门禁 | **没有任何自动化测试**；`pnpm lint` 依赖的 eslint 未安装 |

**做得好的地方**

1. 分层清晰：`api/v1` 只做参数与编排，业务集中在 `services/`，模型与方言差异收在 `db/types.py`、`db/dialect.py`。
2. 双库抽象不是嘴上说说：`BigInteger().with_variant(Integer, "sqlite")`、`AwareDateTime`、`ilike()`、`DatabaseLock`（PG advisory lock / 文件锁）都落到了代码。
3. 预警做成了规则对象（`AlertRule` + `AlertCandidate` + 去重键 + 状态机 + 处置流水），加第 12 条规则只需加一个类。
4. 附件服务的安全细节到位：路径穿越校验、扩展名白名单、大小限制、UUID 落盘、软删 + purge 分离。
5. 认证体系完整：state / nonce / PKCE、一次性登录码、密钥 Fernet 加密、防开放重定向（`safe_redirect_after`）。
6. 前端工程质量高于同类项目：TanStack Query 统一缓存、`useCan()` 订阅式权限、`DataTable` 自适应高度、跨账号清缓存的坑都处理过。

**结论**：业务建模与代码整洁度是加分项；**短板集中在"权限只做了半套"和"SQLite 这条默认路线缺少验证"**，这两类问题会让"能跑通的演示"在真实使用中暴露。

## 二、P0 级问题（功能失效 / 权限越界，建议立即修）

### P0-1　SQLite 下预警"自动关闭"与"超时升级"必然失败（已实测）

- 模型 `app/models/alert.py:83` 把 `AlertAction.operator_id` 定义为 `nullable=False`。
- 迁移 `alembic/versions/0003_alert_action_nullable.py` 把它改成了可空——**但 SQLite 不走 Alembic**：`app/db/session.py:101` 用 `Base.metadata.create_all()` 按模型建表。
- 结果：SQLite 库中该列仍是 `NOT NULL`（实测 `PRAGMA table_info` 返回 notnull=1，插入 NULL 报 `IntegrityError: NOT NULL constraint failed`）。
- 而系统动作恰恰传 `None`：`alert_service.py:121`（自动关闭）、`alert_service.py:447`（超时升级）。

**影响**：默认部署（Windows 便携版 / 单机 SQLite）下，只要有一条预警被自动关闭或超时升级，整个事务回滚——扫描/升级"看起来跑了"，实际什么都没落库。

**修复**：模型改为 `nullable=True`；已有库用一次性 DDL 重建 `alert_action`（SQLite 不支持 ALTER COLUMN）；补一条"新库与迁移一致性"的冒烟测试。

### P0-2　子项目负责人 / 填报人看不到任何预警（已实测）

`AlertService.list_alerts`（`alert_service.py:256-267`）只用 `major_ids` / `college_ids` 收敛范围，没有 SELF 分支；`my_todo`（`571-581`）对 SELF 用户只放行"本人已认领"。

实测（T001，角色 SUB_OWNER + REPORTER，scope=SELF）：其名下子项目 1/2/6 有 7 条预警（4 条 CLAIMED、3 条 PENDING），**接口返回 0 条；"我的督办"待处置数也是 0**。

**影响**：系统最主要的使用者（负责人/填报人）登录后预警中心是空的，只能靠管理员口头通知——预警闭环断在第一环。

**修复**：`list_alerts` 增加 `Alert.sub_id.in_(select(ProjSub.id).where(ProjSub.owner_id == user.id))` 分支（与 `scope.can_access_alert` 口径对齐）；`my_todo` 同步。

### P0-3　9 个业务接口完全没有鉴权

通过 FastAPI 路由表反射得到（已排除 `/api/health`、认证入口与前端回退）：

| 接口 | 泄露内容 |
|---|---|
| `GET /api/progress/school` | 全校进度、各重大项目进度 |
| `GET /api/progress/sub/{sub_id}/trend` | 任意子项目 90 天进度曲线与留痕推断 |
| `GET /api/system/users/picker` | 全校在职人员姓名、工号、所属学院（可遍历） |
| `GET /api/system/roles` | 角色清单与权限数量 |
| `GET /api/system/holidays` | 免填日历 |
| `GET /api/system/import/templates/{kind}` | 导入模板 |
| `GET /api/reports/options`、`/reports/period` | 报表开关与周期 |
| `GET /api/export/fields` | 导出字段定义 |

**影响**：前两项是真实数据泄露（`sub_trend` 还能反推填报节奏），`users/picker` 等于开放了通讯录。文档中"登录后才能访问"的假设不成立。

**修复**：统一加 `user: CurrentUser = Depends(get_current_user)`；`sub_trend` 补 `assert_sub_access`；`picker` 保留登录即可但加限流。

### P0-4　写接口普遍缺少数据范围校验（水平越权 / IDOR）

功能权限做了，**数据范围只在列表查询里做**。以下接口只要拿到权限点，就能操作任意对象：

| 接口 | 现状 | 应校验 |
|---|---|---|
| `POST /api/subs/{id}/progress` | 仅 `progress:update` | `assert_sub_access` |
| `PUT /api/subs/{id}`、`POST /api/subs` | 仅 `project:sub:edit` | 目标子项目/大项目在范围内 |
| `POST /api/majors/{id}/colleges` | 仅 `project:college:edit` | 大项目在范围内 |
| `POST /api/reports` | 仅 `report:fill` | `assert_sub_access` |
| `POST /api/reports/weekly-draft` | 无任何校验 | `assert_sub_access` |
| `GET /api/progress/major/{id}` | 仅登录 | `get_major(id, user)` |
| `POST/PUT/DELETE /api/risks*` | 无 `user` 依赖 | 风险的 major/sub 在范围内 |
| `GET /api/attachments/{id}/download|preview` | 仅登录 | 附件的 `biz_type/biz_id` 在范围内 |

另外 `progress_service.update_progress` 判断"代填"只看 `operator.id != sub.owner_id`，不校验 `progress:onbehalf`——REPORTER 只要绕过前端就能给别人代填（与上一条叠加）。

### P0-5　预警处置接口不校验功能权限

`POST /api/alerts/{id}/claim|close|ignore|transfer`（`alert.py:152-204`）只有 `get_current_user` + 范围校验，**没有 `alert:claim` / `alert:close` / `alert:transfer`**。系统里定义了这三个权限点、角色矩阵里也做了区分（VIEWER 没有 `alert:claim`），但接口层没落地——任何能看到该预警的人都能关闭它。

## 三、P1 级问题（正确性 / 性能 / 可维护性）

### P1-1　SQLite 没有升级通道，模型与迁移已漂移

`init_db()` 用 `create_all` 建表后，`alembic_sync.py:28` 直接把版本标记写成 head。`create_all` 只建缺失的表、**不改已有表结构**，因此后续任何迁移在 SQLite 上都不会执行——P0-1 就是这种漂移的第一个受害者（库里是 `0004_attachment`，代码是 `0005_role_perms`）。

**建议**：SQLite 升级改为"版本比对 + 显式迁移脚本"（或干脆每次发版重建 + 数据导入），并在 CI 里跑一次"空库建表 vs Alembic 建库"的 schema diff。

### P1-2　AL-09 的 `distinct(*cols)` 在 SQLite 上失效

`progress_rules.py:271` 用 `.distinct(major_id, college_id)`。这是 PG 的 `DISTINCT ON`；SQLAlchemy 在 SQLite 上退化为整行 `SELECT DISTINCT`（已编译验证），而查询里带 `proj_sub.id`，等于"不去重"。

**影响**：同一"学院未指定负责人"会在 SQLite 上按子项目数量生成 N 条 AL-09，PG 上只有 1 条；同时该写法已被 SQLAlchemy 标记为 deprecated，未来版本会直接 `CompileError`。

**修复**：改成 `GROUP BY major_id, college_id` + `MIN(sub_id)`，或用 `postgresql.distinct_on()` 加方言分支。

### P1-3　忽略 / 关闭后，次日会重生同一条预警

`_create_or_merge`（`alert_service.py:136-146`）只查 `PENDING/CLAIMED` 且限 7 天窗口。用户点"忽略"后状态变 `IGNORED`，下次扫描不再合并 → 新建一条同样的预警。

**建议**：忽略时写一条抑制记录（`dedup_key + 有效期`），扫描时先查抑制表；或把 `IGNORED` 纳入合并判断并累加 `merged_count`。

### P1-4　报表提交不校验截止时间与补填期

`report_service.submit`（`127-195`）只判"子项目存在/未结项/类型合法"，`is_due` 与 `deadline_of` 只用于展示和待填清单。用户可以补填任意久远的周报，也可以提交**未来周期**；文档里的"逾期 3 日内可补填、超期需开权限"没有落地到提交路径。

### P1-5　8 个系统参数是"装饰性"的

在"参数配置"页可改，但代码里从未读取：`aggregate.school.mode`、`aggregate.include_closed`、`notify.digest.hour/minute`、`notify.sms.enabled`、`notify.email.enabled`、`system.session_idle_minutes`、`alert.AL-08.days`。另有 `system.audit_retention_years` / `snapshot_retention_years` 只读环境变量、不读 `sys_config`。

**影响**：管理员改完没有任何反馈，比"没这个开关"更伤信任。建议要么接线，要么从页面隐藏并标注"预留"。

### P1-6　加权汇总的"缺权重"口径与注释不符

`aggregation_service.py:44-63` 注释写"权重缺失按等权"，实现是缺失按 0：当部分子项目有权重、部分没有时，没权重的那些**整体被剔除**（例：权重 [3, None]、进度 [100, 0] → 结果 100）。学院进度会因此虚高。

### P1-7　N+1 查询，规模上去会明显卡（已实测）

| 场景 | 实测 SQL 条数 | 放大后 |
|---|---|---|
| 进度总表（7 个子项目） | 11 条 | ≈1 + N，N=500 时 500+ 条 |
| 及时率（30 天 / 7 个子项目） | 37 条 | ≈子项目数 × 期次数，500 项目 × 1 年可达数千条 |
| 大项目列表（接口层） | 每个大项目再查 1 次学院 + 每学院 1 次子项目数 | 20 个大项目 × 5 学院 ≈ 200 条 |

`progress_service.table` 还把所有子项目读进内存后**在 Python 里排序分页**，`sub_view` 每个子项目再查一次"最后一次留痕"。建议：留痕用窗口函数一次取回；分页/排序下推到 SQL；`list_major_colleges` 的 sub_count 改 `GROUP BY` 聚合。

### P1-8　审计日志会把 token 写进库

`deps.py:107-109` 支持 `?token=` 传令牌（用于下载/SSE），而 `audit.py:80-84` 把 `request.query_params` 原样写进 `audit_log.detail`。凡是带 token 的写请求，令牌就会以明文留在审计表里，而审计页对 `system:audit` 角色可见。

**修复**：审计写入前过滤 `token` / `access_token` / `password` 等键；或把下载鉴权改成短时一次性票据。

### P1-9　配置缓存跨进程不同步

`ConfigService` 的缓存是**类变量**（进程级），`PUT /configs/{key}` 只清当前进程。多 worker / 多实例部署时，其它进程会一直用旧阈值，直到重启——而 README 恰好宣传多实例部署。

### P1-10　默认密钥与调试开关

`config.py:25` 的默认 `secret_key` 是 `dev-secret-change-me-in-production`；仓库内 `backend/.env` 里 `PM_SECRET_KEY` 仍是占位文案（18 字符）、`PM_DEBUG=true`。虽然 `.env` 应被 gitignore，但随包分发时一旦被复制，JWT 可被伪造、`/docs` 会暴露。

## 四、P2 级问题（工程化与一致性）

1. **零测试**：`requirements.txt` 里有 pytest，仓库里没有任何测试文件；权限、预警规则、双库兼容这三块最需要回归测试。
2. **`pnpm lint` 跑不起来**：`package.json:11` 调用 `eslint`，`devDependencies` 里没有 eslint 及其配置。
3. **README 数字失真**：写"84 个 API"（实际 103）、"27 张表"（实际 23）、"6 个迁移"（实际 5），迁移表格只列了 3 条。
4. **仓库根目录有调试残留**：`_check_perm.py`、`_deploy_fix.py`、`_deploy_perm.py`、`_menu.cjs`、`_menu-admin.png`，以及空的 `scripts/` 目录；`.work/`、`pm-windows-portable.zip`（42 MB）也在工作区。
5. **错误响应格式不统一**：业务异常走 FastAPI 的 `{"detail": ...}`，正常响应走 `{"code","message","data"}`。前端两种都兼容了，但对外文档只写了后者。
6. **`@app.on_event` 已废弃**：`main.py:150/164` 应改 `lifespan`（FastAPI 0.146 下会有弃用告警）。
7. **`job_daily_digest` 是空壳**：`scheduler.py:121` 有 `... if False else None` 的死代码，摘要从未真正发送；`_notify` 也只是写日志（注释已承认"一期只记日志"）。
8. **阈值硬编码**：`progress_service._is_near_deadline` 写死 30 天 / 80%，而 AL-05 读参数——同一件事两个口径，参数一改页面提示就与预警不一致。
9. **前端路由无权限守卫**：只判"有没有 token"，直接输 URL 能进无权限页面（接口会 403，但页面空白 + 一串报错）。
10. **遗留字段**：`acceptance_*`、`budget_*`、`evaluation_*` 在模型里，接口与页面都没有入口——需求第 32/33/34/42 项预留，建议在文档里明确"二期"。
