## 一、一句话结论

**框架和"读"的链路是完整的（数据建模、权限矩阵、11 条预警规则、报表周期、导出、索引、测试都有），
但"推给人—人去处理—处理完有反馈—失败有兜底"这四段在多个主链路上是断的。**
最典型的三个断点是：**站内消息没人能读**、**橙色预警没有任何真实触达**、**作废一张历史报表等于制造一条永久缺报**。

按"闭环断在哪一环"归类，共 **6 类 11 个 P0**、**23 个 P1**、**若干 P2**。

## 二、闭环缺口的六种形态（这是问题的本质分类）

| 形态 | 含义 | 本项目中的典型例子 |
|---|---|---|
| **A. 有发送无接收** | 动作执行了、状态记成功，但目标人永远看不到 | 站内消息只写 `notify_log` 就置 SUCCESS；催办、每日摘要、超时升级全部落在这里 |
| **B. 有状态无出口** | 对象进入某个状态后，没有任何界面/接口能把它推出去 | 报表 `VOIDED` 后无法回到 `SUBMITTED`；补填放行只能"开"不能"看/撤"；预警处置流水 `alert_action` 无人读取 |
| **C. 有计算无展示** | 后端算得出、前端没有页面 | 全校进度 `GET /progress/school`、大项目进度汇总 `GET /progress/major/{id}` 零调用；预警触发详情 `candidate.detail` 从不落库 |
| **D. 有配置无消费** | 参数页可改，代码不读 | `aggregate.school.mode`、`system.session_idle_minutes`、`system.audit/snapshot_retention_years`（均已在页面标"预留"）；`alert.AL-04/06/09/10/11.enabled` 根本不在配置表里 |
| **E. 有异常无补偿** | 失败只写日志，无重试/告警/人工入口 | 6 个定时任务失败只 `logger.exception`；备份失败静默；通知重试被 SKIPPED 记录堵死 |
| **F. 有权限点无校验** | 权限矩阵里有，接口/按钮不校验 | `export:ledger`、`export:progress`、`progress:onbehalf`、`project:check`、`dashboard:view` 五个权限点是死的；三个导出接口只要求登录 |

## 三、P0：业务走不通 / 数据会错（11 项）

### 3.1 通知触达整条链断（A + E）

**现象**：
1. `_notify(INNER)` / `NotifyService.deliver()` 对站内通道"写库即成功"（`notify_service.py:59-62`、`alert_service.py:247-254`）。
2. `notify_log` 表只有 `receiver_id` 和状态，**没有标题/正文/已读字段**（`models/system.py:163-177`）。
3. 全系统没有"我的消息"接口，唯一能读通知的 `GET /api/system/notify-logs` 需要 `system:audit`（`system.py:471-476`）——那是管理员运维视角。
4. 橙色预警**不发邮件**（`alert_service.py:183-191` 只在 `RED` 时发 EMAIL/SMS），而橙色占 11 条规则里的 6 条。
5. 通知重试把 `SKIPPED` 也算进队列且按 id 升序 `limit 100`（`notify_service.py:78-93`）——SKIPPED 的 `_attempts()` 恒为 0，永远不被跳过，**真 FAILED 永远排不上**。
6. 每日摘要把统计 JSON 塞进 `NotifyLog.error`（`scheduler.py:186-196`），`deliver()` 失败立刻用错误文案覆盖 `error`（`notify_service.py:112-126`），`_compose_digest` 再解析只剩全 0。

**实测**：运行库 42 条通知里 18 条未成功（EMAIL FAILED 12、SKIPPED 6）；`backend/.env` 的 `PM_SMTP_PASSWORD` 为空。
**闭环断点**：`发得出 → 存得下 → 有人读 → 有已读回执` 这四段只做了前两段。
**建议**：新增 `sys_message`（含正文/read_at）+ `GET /api/messages`、`unread-count`、`POST /{id}/read`；顶栏加铃铛；橙色补邮件；重试只查 `FAILED`；摘要正文独立字段。

### 3.2 作废历史报表 = 永久缺报（B）

`submit()` 的补填期校验（`report_service.py:161-168`）排在"作废可复活"分支（`:177-186`）**之前**。
超过「截止 + `report.correct_days`」的报表一作废，重填就被同一校验拦住；该期变成 `OVERDUE`，AL-06/AL-07 下一轮扫描立刻重建。

**实测**：作废 20 周前的周报后重填 → `400 已超过补填期（截止 2026-06-08 12:00，可补填 3 天）`。
代码注释写着"作废后允许重新提交，原来这里直接 raise 导致永久缺报"——**只对补填期内成立，历史周期仍死循环**。
**建议**：作废时自动开一条覆盖该周期的 `ReportGrace`，或复活分支跳过补填期校验。

### 3.3 预警每天被"关闭再重建"（B）

`job_hourly_scan` 在每小时 :05 调 `scan(date.today())`（`scheduler.py:99-114`），但当天快照要到 01:00 才生成（`:59-79`）。
AL-03 只查 `snap_date = 当天`（`progress_rules.py:132-143`），候选为空 → `_auto_close` 判定"触发条件已消除"批量关闭 → 01:00 快照后再新建。

**实测**：清空当天快照后 `scan()` 返回 `auto_closed=4`，AL-03 的 PENDING 从 1 条变成 0 条。
**影响**：每条停滞预警每天被关一次建一次，`merged_count` 与统计全失真，关闭理由造假。
**同源问题**：AL-06 只盯"上一个自然周"（`report_risk_rules.py:49`），一周后旧缺报不再进候选，被自动关闭并**永久遗忘**；月报从未被任何规则覆盖。

### 3.4 报表截止时间整体晚 8 小时（数据错）

`deadline_of()` 用 `datetime.combine(d, time(12,0), tzinfo=UTC)` 拼北京时间语义（`report_service.py:70/83/97`）。

**实测**：`WEEKLY 2026-10-12 → 2026-10-19 12:00+00:00`（北京 20:00）；日报次日 08:00；月报次日 02:00。
**影响**：及时率 ON_TIME/LATE 边界整体偏移，教师凭空多 8 小时；与 AL-06 的另一套硬编码口径叠加后，同一个"逾期"两套结果。

### 3.5 权限与数据范围反向断裂（F）

| 问题 | 证据 |
|---|---|
| 大项目负责人（SELF 范围）能列出自己项目，点详情 **403** | `project_service.py:180-191` 的 `get_major` 不认 `owner_id`，而写权限 `scope.py:131-145` 认 |
| MAJOR / COLLEGE 范围用户大项目列表**恒为空** | `ProjMajor` 没有 `major_id/college_id` 列，`apply_scope` 命中 `where(false())`（`scope.py:42-65`） |
| 学院负责人**建不了子项目、结不了项、催不了办** | `COLLEGE_OWNER` 缺 `project:sub:edit`、`progress:urge`（`permissions.py:67-73`） |
| 项目总负责人有 `report:void`，与"作废仅管理员"冲突 | `permissions.py:87` vs 需求 3.4 / 附录二 |

**实测**：MAJOR 范围用户 `list_majors total=0`，但 `get_major(1)` 放行。
**另**：`GET /progress/major/{id}` 无权限点、无范围校验（`progress.py:140-149`），任意登录用户可枚举任意大项目进度构成。

### 3.6 全新部署缺 `report:grant`，逾期补填在新装环境完全不可用

`ALL_PERMISSIONS` 39 项（`permissions.py:15-33`），但 SQLite 种子 `perms` 只写了 **38 项**（`session.py:296-335`）；`0007_report_grace.py` 只补**存量库**。
**实测**：全新库 `sys_permission = 38`、`report:grant = 0`，没有任何角色持有 → 除 SYS_ADMIN 短路外无人能开"逾期补填"，前端按钮也不显示。

### 3.7 第三方登录 7 种协议端到端断裂

后端回调 `GET /api/auth/{kind}/callback` 直接 `return ok(data)` 返回 JSON（`auth.py:124-143`）；
前端有落地页 `/login/oidc/complete`（`App.tsx:89`）、`OidcCallback.tsx:19` 从 query 读 `login_code`，但**没有任何代码把浏览器跳过去**。
用户授权完停在**一屏 JSON**。OIDC / OAuth2 / CAS / SAML2 / 飞书 / 钉钉 / 企业微信 7 种全部不可用；账号绑定同理。
LDAP（`flow='post'`）也没有登录表单（`Login/index.tsx:50` 只渲染 redirect 类型）。

### 3.8 备份 / 恢复不闭环（E）

- `scripts/backup.py` 只有 `pg_dump` 分支，**默认的 SQLite 部署每日备份必失败**（`do_backup()` 直接 `find_pg_dump()`）。
- `release.sh` 只 `cp pm.db`，PG 部署发布前无备份。
- 全系统**没有任何恢复入口/恢复校验**；`--verify` 找不到 `pg_restore` 时静默返回成功。
- 文档写着"自动备份已内置，每日 02:00"，与实现矛盾。

### 3.9 便携版"解压双击即用"实际起不来

`pack-portable.ps1` 不复制 `.env`/`.env.example`，`start.bat` 模板不设 `PM_SECRET_KEY`；
非 debug 下 `Settings._check_secret_key` 直接抛 `ValidationError`（`config.py:48-72`）。交付给学校的便携版第一次双击必然失败。

### 3.10 结项闭环缺失

- 只校验 `current_progress == 100`（`project_service.py:417-421`），**不查材料、不查未关闭预警、不校验确认人**。
- 需求 6.1 第 6 项要求"进度 100% + 材料齐 + 无未关闭预警 + 学院负责人确认"，一条都没做。
- **实测**：子项目带着 18 条未关闭预警也能直接结项成功。
- 结项后仍可改（**实测** `PUT /api/subs/1` 改名称/计划/权重全部 200），与"结项后只能看不能改"不符。

### 3.11 报表更正闭环断裂

- 前端 `Report/List.tsx:151-170` 只有"查看/作废"，**没有"更正"入口**；填报页只能提交当前周期。
- 后端 `_check_correct_permission` 用 `project:sub:edit` 冒充"学院负责人开权限"（`report_service.py:229-241`），而学院负责人恰恰没有这个权限点；`report_grace` 只作用于补填，**对更正无效**。
- 需求 3.4 的"3 天内自己改、超 3 天学院负责人开权限"两段都走不通，只能找管理员作废——而作废又会踩 3.2 的坑。

## 四、P1：链路残缺 / 口径不符（23 项，按主题合并）

## 六、确实已闭环的部分（不是全盘否定）

以下经逐行核对 + 实测确认**入口、数据、状态、反馈都通**，不必返工：

**业务建模**：三级责任体系与硬约束（子项目必须同时归属大项目+学院）、权重加权汇总（缺权重按 1、Σ=0 退化等权）、偏差识别、免填期计时暂停、11 条规则对象化、7 天同源合并、AL-09/AL-10 不可手工关闭 + 自动关闭路径、接收人兜底链、预警折叠聚合、预警按时处置率口径。

**进度**：两处填报入口、每次改动留痕（`prog_record` 只增不改）、回调必填原因、代填 `on_behalf_of`、数据可信度灰显（21 天）、进度总表默认按偏差排序 + 只看异常、**子项目趋势曲线（有页面有菜单真调接口）**、**学院对比页（同上）**、`last_note` 自动带出。

## 八、说明：哪些不算缺陷

以下**不应计入开发缺陷**，审计时已单独区分：

- **已明确列入二期**（需求 6.3 第 32–42 项）：验收记录、经费明细、项目文档库、工时统计、后评价 —— `proj_major` 上的 `acceptance_*` / `budget_*` / `evaluation_*` 是预留字段，符合定位。
- **需求方尚未确认**：看板 4 张图（第 41 项）、结项退回机制（第 27 项）、附件节点清单（第 26 项）、`aggregate.school.mode` 的 WEIGHTED 语义。
- **明确不做**：审批流、移动端、企业微信、合作企业账号、导出固定表样、里程碑自动算进度。

这些如果在验收时被校方按"通用项目管理软件"标准要求，会变成争议 —— 建议在需求文档 6.3 里把"一期不做"写死。
