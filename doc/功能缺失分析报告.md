# 与通用项目管理软件对比：功能缺失分析

> 对比对象：`doc/产教融合项目管理系统-需求方案说明书-V1.3.docx`（本报告结论已并入 V1.4 的 6.3 节，编号 32–42）
> 参照基准：通用项目管理软件的标准能力（Project / 禅道 / Teambition / 飞书项目 / 钉钉项目 / Jira 等）
> 分析日期：2026-10-19

---

## 一、结论先行

**有缺失，而且分三种性质，处理方式完全不同：**

| 类别 | 数量 | 性质 | 处理建议 |
|---|---|---|---|
| **A 类：真缺失，且影响业务闭环** | 7 项 | 方案没提，但业务上绕不过去 | **必须补**，否则上线后必然被要求加 |
| **B 类：通用软件有，本方案有意不做** | 4 项 | 是"轻填报"定位下的主动取舍，合理 | **不用补，但必须写进文档**，明确"一期不做"，否则验收时说不清 |
| **C 类：通用软件有，一期可不做** | 9 项 | 增强项，不影响跑通 | 列入二期，文档里留一句"二期评估"即可 |

**一句话判断**：这套方案在"**进度填报 + 预警督办**"这一条线上做得比通用软件更贴学校实际（三级责任、防预警泛滥、减填报负担）；但在"**项目管理的完整性**"上有明显短板——**没有依赖关系、没有甘特图、没有基线、没有预算、没有文档库、没有验收**。它更像一个"进度督办系统"，而不是完整的"项目管理系统"。

---

## 二、A 类：真缺失，且影响业务闭环（7 项）

### A1. 任务依赖关系（前置/紧后）——最根本的缺失

| | |
|---|---|
| **通用软件** | 任务之间可设"完成-开始""开始-开始"等 4 种依赖，据此自动排期、算关键路径、分析延期传导 |
| **本方案** | **完全没有**。全文"依赖"只出现在"统一身份认证存在外部依赖"和"依赖管理人员个人记忆"，与任务关系无关 |
| **影响** | ① 算不出关键路径，管理者不知道"哪条线一拖就全线拖"<br>② 无法回答"这个子项目晚了，会影响后面哪个"<br>③ 计划时间只能靠人拍脑袋填，系统无法校验合理性 |
| **建议** | 一期可只做**最简单的"前置子项目"字段**（一个子项目可填 1–N 个前置），不做自动排期，但至少能画出依赖箭头、能提示"前置未完成"。**成本很低，价值很高。** |

### A2. 甘特图

| | |
|---|---|
| **通用软件** | 甘特图是标志性视图：横轴时间、纵轴任务、条形表示工期、箭头表示依赖、竖线表示今天 |
| **本方案** | 只有**进度曲线**（实际进度 vs 时间进度两条线，针对单个子项目）和**进度总表**（表格）。文档明确写"人工填写进度百分比，**不采用里程碑自动计算**" |
| **影响** | 校级/大项目负责人要看"整体时间布局"时，表格和曲线都给不出"哪几件事在并行、哪几件挤在一起"。这是汇报会上最常被问的 |
| **建议** | 增加**只读甘特图**（不要求教师维护，直接用已有的计划起止时间画条）。数据都是现成的，**纯前端工作量**，性价比最高的一项补充。 |

### A3. 基线（Baseline）

| | |
|---|---|
| **通用软件** | 可冻结一版计划作为"基线"，之后对比"基线 vs 当前计划 vs 实际"，三次偏差一目了然 |
| **本方案** | **没有基线概念**。偏差算的是"实际进度 vs 时间进度"，**计划一改，时间进度立刻按新计划重算，历史对比全部失效** |
| **影响** | 这正是 6.3 第 15 项（项目变更）要确认的痛点根源。没有基线，就永远回答不了"这个项目比原计划晚了多少"——只能回答"比当前计划晚了多少" |
| **建议** | 一期至少保留**"原始计划起止时间"字段**（立项时锁定，变更时只改"当前计划"），这样能算出"相对原计划的延期天数"。**改动极小，但能救活所有历史对比。** |

### A4. 预算 / 经费 / 成本管理

| | |
|---|---|
| **通用软件** | 预算编制、实际支出、成本偏差、经费执行率 |
| **本方案** | **完全没有**。全文"预算""成本""资金""报销""采购"命中数均为 0；"经费"仅出现 1 次，且是"一期**不按经费金额折算**全校进度" |
| **影响** | 产教融合项目**必然涉及经费**：企业投入、设备采购、实训耗材、师资培训。学校验收时"经费执行率"是硬指标。现在系统只管进度不管钱，等于只做了一半 |
| **建议** | 一期可只做**"项目预算总额 + 已执行金额"两个字段**（手工维护，不做报销流程），能算执行率即可。**不做明细账，但要有总数。** |

### A5. 文档库（过程材料管理）

| | |
|---|---|
| **通用软件** | 独立文档库：目录树、版本管理、在线预览、全文检索、权限控制 |
| **本方案** | 只有**报表附件**（挂在日/周/月报上）。"资料库""知识库""在线预览""全文检索"命中数均为 0 |
| **影响** | 文档 1.2 节自己列的痛点之一是"**过程材料难归集**"——日报周报散落各处。但方案只解决了"报表在线"，没解决"材料归集"。协议、方案、照片、验收报告这些**不属于任何一张报表的材料，无处可放** |
| **建议** | 增加**按项目归档的附件区**（不要求版本管理，只要"项目 → 材料分类 → 文件"三级），支持按项目/类型检索、导出打包。这是 1.2 节痛点的直接对应项。 |

### A6. 验收管理

| | |
|---|---|
| **通用软件** | 验收标准、验收清单、验收记录、验收结论（通过/整改/不通过） |
| **本方案** | 只有**结项**（进度 100% + 材料齐 → 学院负责人确认）。"验收"12 次全部是"**用于**项目验收""**验收前**才发现"这类**外部事件**描述，系统内无验收功能 |
| **影响** | 结项 ≠ 验收。产教融合项目通常要接受**学校验收 + 上级（教育厅）验收**，验收要整改、要复验。现在结项后子项目就"只读"了，整改无处记录 |
| **建议** | 增加**验收记录**：验收时间、验收单位、结论、整改事项、整改完成时间。哪怕只做一个表单，也能让"结项后"这段不再空白。 |

### A7. 后评价 / 成效评价

| | |
|---|---|
| **通用软件** | 项目后评价、收益实现跟踪 |
| **本方案** | **没有**。文档 1.5 节列了 6 项"预期成效"指标（台账完整率、及时率、材料留存率…），但**这些是评价"系统用得好不好"，不是评价"项目建得好不好"**。项目本身成效（学生就业、企业满意度、课程开出率）无任何采集 |
| **影响** | 产教融合项目最终要回答"产教融合成效如何"。现在系统能证明"我们按时填报了"，但证明不了"项目产生了什么效果" |
| **建议** | 一期可在结项时增加**一张成效登记表**（按项目类型配 3–5 个指标，如订单班人数、企业投入额、双师认定人数），只做录入与汇总，不做复杂分析。 |

## 三、B 类：通用软件有，本方案有意不做（4 项）

这 4 项**不是遗漏，是取舍**，而且取舍方向是对的。但**必须在文档里写明"一期不做"**，否则验收时校方按通用软件的标准要求，就会变成争议。

| 项 | 通用软件 | 本方案 | 为什么取舍合理 | 文档该怎么写 |
|---|---|---|---|---|
| **B1. 审批流** | 立项审批、变更审批、结项审批 | **明确不设审批**（报表、结项都是"提交即生效"） | 审批是填报负担的最大来源。文档判断"审批一多，数据就假"是对的 | 已在 6.1 第 6 项写明"不设审批"，但**立项环节**没有说明。建议补一句：立项审批在 OA 走，系统只接收已批项目 |
| **B2. 里程碑自动计算进度** | 里程碑完成 → 进度自动跳 | **人工填百分比**，明确"不采用里程碑自动计算" | 里程碑要维护，教师不会维护；人工填反而更真实 | 已写明，但建议补一句"如需里程碑视图，二期评估" |
| **B3. 移动端** | App / 小程序 | **仅 PC 端** | 已确认的范围决定 | 已在 6.2 第 11 项写明 |
| **B4. 工时 / 人天统计** | 工时填报、人天汇总、人力成本 | **没有** | 教师填工时会强烈抵触，且产教融合项目不是按工时结算 | **没写**。建议在"边界事项"里补一条："一期不做工时统计" |

> **关键提醒**：B 类最容易被忽略的是 **B4 工时**——通用软件几乎都有，校方可能默认"应该有"。不写清楚，验收时就是坑。

## 四、C 类：通用软件有，一期可不做（9 项）

| 项 | 说明 | 建议 |
|---|---|---|
| C1. 协作（评论/@/讨论） | 现在只有"催办"这一个单向动作，无法在子项目下讨论 | 二期；一期可用"催办+说明"凑合 |
| C2. 消息中心（已读未读） | 有通知，但没有统一的消息中心、已读状态、通知偏好 | 二期；一期站内消息+邮件够用 |
| C3. 项目模板 / 复制项目 | 5 类项目结构相似，现在新建要重新填一遍 | **建议一期就做**（成本低），或至少支持"复制已有项目结构" |
| C4. 自定义字段 | 5 类项目字段需求不同（订单班要"学生人数"，实训基地要"设备清单"），现在字段固定 | 二期；一期可用"备注"兜底 |
| C5. 优先级 / 项目组合视图 | 多个大项目之间没有优先级，校级看不到"哪些更重要" | 二期；一期可按状态/预警数排序 |
| C6. 资源负载视图 | 一个教师参与多个项目，是否冲突、是否超负荷，看不到 | 二期；依赖 B4 工时，一期做不了 |
| C7. 日历视图 | 项目日历、节点日历 | 二期；与甘特图（A2）一并考虑 |
| C8. 数据看板 / 图表 | "看板"只出现 1 次（"查看者查看看板"），但**没定义看板有哪些图** | **建议一期明确**：至少 4 张图（全校进度分布、学院对比、预警趋势、及时率趋势） |
| C9. 项目健康度评分 | 通用软件常有"红黄绿"健康度 | 二期；一期用预警数代替 |

> **C8 值得单独说**：文档多处提到"看板""统计""曲线""对比"，但**从未定义看板长什么样、有几张图**。这是需求缺口，不是功能缺失——开发时必然要问。

## 五、还有两个"隐性缺失"（比功能缺失更危险）

### 隐性缺失 1：功能清单与使用场景对不上

文档第五章描述了大量日常动作，但**第三章功能清单里没有对应条目**：

| 第五章说的动作 | 第三章功能表里有吗 |
|---|---|
| "我的督办"页面（三个数字卡 + 待办清单） | ❌ 没有 |
| "直接发起催办" | ❌ 没有 |
| "看板" | ❌ 没有定义 |
| 进度曲线、学院对比 | ⚠️ 3.2 正文提到，但不在 3.1 功能表里 |

> 已在 6.3 第 25 项把"催办"补进确认清单，但**"我的督办"页面和"看板"仍未定义**。建议补进 6.3 或 3.2。

### 隐性缺失 2：只覆盖"执行期"，不覆盖"立项前"和"结项后"

系统的生命周期是：**立项建档 → … → 结项归档**。

- **立项前**没有：项目申报、评审、批复（这些在 OA 走，合理）
- **结项后**没有：验收、整改、后评价、成果沉淀（**这是真空白**，见 A6、A7）

结果是：系统只管"项目在做的时候"，做完就归档了。但学校真正要交差的恰恰是"做完了效果如何"。

## 六、优先级建议

如果只能补 3 件事，按性价比排序：

| 排序 | 补什么 | 理由 | 工作量 |
|---|---|---|---|
| **1** | **甘特图（只读）** | 数据现成（计划起止时间），纯前端；汇报会上最有用 | 小 |
| **2** | **原始计划基线字段** | 一个字段，救活所有历史对比；是 6.3 第 15 项的根 | 极小 |
| **3** | **项目文档库（附件归档区）** | 直接对应 1.2 节"过程材料难归集"这个原始痛点 | 中 |

其次：**验收记录**（A6）、**预算总额字段**（A4）。

可以不做但要写清楚的：**工时（B4）**、**看板定义（C8）**。

## 七、一句话总结

> 这套方案**不是通用项目管理软件的简化版，而是另一类产品**——它把力气花在"让教师愿意填、让管理者看得见问题"上，这部分做得比通用软件好；代价是**放弃了通用软件的项目管理骨架**（依赖、甘特、基线、预算、文档、验收）。
>
> 所以判断"有没有缺失"，取决于学校要的是**"进度督办工具"还是"项目管理系统"**。如果是前者，缺 A1–A3 里最轻的那几个就够了；如果是后者，A 类 7 项**一项都绕不过**。
>
> 建议：在需求确认会上**把这个问题直接问校方**——"这个系统是只管进度督办，还是要管项目全生命周期？"答案不同，工作量和报价差一倍以上。
