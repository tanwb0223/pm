## 四、当前问题

### P1-1　SQLite 库缺全部 40 条二级索引（已实测）

索引只在 `alembic/versions/0001_init.py` 里用 `op.create_index` 创建，共 40 条（`idx_sub_major`、`idx_record_sub_time`、`idx_alert_status`、`idx_audit_time`、`idx_notify_receiver` …）。而 SQLite 部署**不走迁移**：`create_all()` 按模型建表，模型里没有 `index=True` 或 `Index()`，`ensure_alembic_stamped()` 又直接把版本写成 head。

实测现有库 `D:/data/pm/pm.db`（只读打开）：

```
表数 25（24 业务表 + alembic_version）
显式索引数 1 —— 只有 ix_report_grace_sub_type（0007 迁移建的）
```

查询计划印证：

```
select * from alert where status='PENDING' order by level
  → SCAN alert + USE TEMP B-TREE FOR ORDER BY
select * from prog_record where sub_id=1 order by created_at desc
  → SCAN prog_record + USE TEMP B-TREE FOR ORDER BY
```

**影响**：同一套代码在 PostgreSQL 上是索引扫描，在默认的 SQLite 部署上是全表扫描 + 临时排序。当前数据量（7 个子项目、19 条留痕）完全无感；按 README 宣传的「500 子项目 / 一学年」规模，进度总表、及时率、预警扫描会同步退化一个数量级。这也解释了为什么「本地演示很顺」而「学校真实数据进来变慢」。

**修复**：把 40 条索引声明到模型（`__table_args__` 里 `Index(...)`），让 `create_all` 也能建；存量 SQLite 库写一段「查 `sqlite_master` 缺哪条补哪条」的幂等 DDL，挂到 `repair_sqlite_schema()` 后面。这是投入产出比最高的一条。

### P1-2　大项目 4 个写接口没有数据范围校验【越权】

`project.py` 里这四个接口签名里连 `user` 都没有：

| 接口 | 行号 | 现状 |
|---|---|---|
| `POST /api/majors` | 168 | 仅 `project:major:edit` |
| `PUT /api/majors/{id}` | 176 | 仅 `project:major:edit` |
| `DELETE /api/majors/{id}` | 184 | 仅 `project:major:edit` |
| `POST/DELETE /api/majors/{id}/colleges` | 208 / 216 | 仅 `project:college:edit` |

`project:major:edit` 的授予方是 `PROJECT_OWNER`（项目总负责人）与 `SYS_ADMIN`（`core/permissions.py:86-92`）。项目总负责人在真实部署里通常是 `MAJOR` 范围，于是**他可以新建、改名、删除任何大项目**，包括自己没被授权的。子项目侧已经用 `can_write_sub_target` + `assert_sub_access` 收口了，大项目侧漏了同一套。

**修复**：`update/delete` 用 `assert_major_access`（按 `major.owner_id` + `major_ids()` 判定）；`create` 用「非全校范围时 `owner_id` 必须是自己」。

### P1-3　示例配置里的密钥是中文占位符，且无启动校验【部署安全】

`.env.example:15` 与仓库内 `backend/.env:10` 都是：

```
PM_SECRET_KEY=请替换为随机字符串（至少 32 位）
```

README 的部署步骤是 `copy .env.example .env`。照做的话，JWT 签名密钥是一个**公开、固定、且来自仓库**的字符串——任何拿到仓库的人都能伪造任意用户的 token（`security.py:44`，HS256）。`config.py:25` 还有个兜底默认值 `dev-secret-change-me-in-production`，同样没有长度/熵校验。

**修复**：`Settings` 加一条 `model_validator`——生产模式（`PM_DEBUG=false`）下密钥长度 < 32 或等于内置占位值就直接拒绝启动；`.env.example` 改成留空 + 注释「必须用 `python -c "import secrets;print(secrets.token_urlsafe(48))"` 生成」。

### P1-4　前端 22 个路由没有权限守卫

`App.tsx:31-37` 的 `RequireAuth` 只判 `token` 是否存在。菜单是按 `useCan()` 过滤的（`layouts/AppLayout.tsx:104-195`），但路由没有——直接在地址栏输 `/system/users`，页面会渲染、发请求、拿 403，然后空白加一串错误提示。

**修复**：加一层 `<RequirePerm code="system:user">` 包装，无权限时 `<Navigate to="/dashboard" />`；顺手把 403 的兜底页做出来，比"空白 + toast"专业得多。

### P1-5　4 个参数仍只在页面上存在

| 参数 | 现状 |
|---|---|
| `aggregate.school.mode` | 聚合服务从不读，永远等权 |
| `system.session_idle_minutes` | 无任何空闲超时实现，token 30 分钟硬过期 |
| `alert.AL-08.days` | `AL08RiskOverdue` 直接用 `plan_close_date`，不读该参数 |
| `system.audit_retention_years` / `snapshot_retention_years` | 只读环境变量 `PM_*`，`sys_config` 里改无效 |

**建议**：要么接线（`AL-08.days` 最简单，给规则加一个默认闭环天数的兜底），要么在参数页标「预留·未生效」，别让管理员改完一脸问号。

### P1-6　登录没有失败限流，令牌有三处边角

- `POST /api/auth/login` 与 `/login/ldap`：**无失败计数、无锁定、无验证码**。Argon2 抗拖库，但扛不住在线撞库。
- `?token=` 传令牌（`deps.py:109`）：审计已脱敏，但 Nginx / uvicorn 的 access log 会原样记下。
- 改密写了 `password_updated_at`（`auth.py:224`），但 `get_current_user` 从不校验 → 改密后旧 token 仍有效至多 30 分钟。
- 无 refresh token：前端 401 直接清登录态跳登录页（`lib/http.ts:47-66`），用户每 30 分钟被踢一次。

**建议**：登录加「同一账号 5 分钟内 5 次失败锁定 15 分钟」（落 `sys_user` 或内存 + 库双写）；`iat < password_updated_at` 即拒；如果不想做 refresh，至少把 `access_token_expire_minutes` 提到 8 小时并让前端在无操作时静默续期。

### P1-7　零测试 + lint 不可用

- `requirements.txt` 里有 pytest，仓库里**没有一个测试文件**。
- `package.json:11` 是 `eslint . --ext ts,tsx`，但 `devDependencies` 只有 7 个包，无 eslint、无配置文件。

最需要回归的三块正好是最容易静默出错的：**权限矩阵**（38 点 × 7 角色）、**双库一致性**（SQLite 建表 vs Alembic 建表，P1-1 就是没人比对才漏的）、**预警规则**（11 条规则 + 去重 + 自动关闭）。

**建议**：不追求覆盖率，先补 3 个冒烟测试——① 空库 `create_all` 后断言索引名齐全（正好锁住 P1-1）；② 每个角色登录后遍历菜单接口，断言 200/403 符合矩阵；③ 造 1 个大项目跑一次 `scan()`，断言 11 条规则的候选数。半天能写完，能挡住后面 80% 的回归。

### P2 级

1. **预警扫描是逐候选查询**：`scan()` 对每个候选调 `_create_or_merge`（`alert_service.py:71-76`），内部一次 `select`。500 子项目 × 11 规则下会是数百条 SQL；`AL-08` 还对每条风险 `db.get(ProjSub)`（`report_risk_rules.py:170`）。建议把「已有未关闭预警」一次性按 `dedup_key` 拉进内存字典。
2. **进度总表仍全量内存排序分页**（`progress_service.py:206-246`）：`s.owner.name` 逐行懒加载，`colleges` / `majors` 每次全表载入。`school_summary` 对每个大项目单独聚合（`progress_service.py:271-274`）。
3. **`only_mine` 语义不对**：`or_(claimed_by == user.id, status == "PENDING")`（`alert_service.py:327-330`）→ 勾上「只看我的」反而返回**范围内所有人的待处置预警**。前端 `Alert/Center.tsx:378` 正是这个复选框。
4. **免填日仍能提交日报**：`submit()` 不调 `is_due()`，只校验截止与补填期（`report_service.py:127-163`）。寒暑假教师仍可手填日报。
5. **`DELETE /attachments/{id}/purge`** 只有 `system:config`、无范围校验（`attachment.py:202-208`），可物理清除任意软删附件。权限点够高，风险有限。

7. **根目录残留 `.deploy-build.log`**；`.env.bak` 也还在（虽已 gitignore）。
8. **错误响应两种格式并存**：业务异常走 FastAPI `{"detail": ...}`，正常响应走 `{"code","message","data"}`。前端两种都兼容了（`http.ts:70-80`），对外文档只写了后者。

## 六、结论

**这一版比 10-21 时明显成熟。** 上一版的 5 个 P0 修掉 4 个，10 个 P1 修掉 6 个，而且修法是对的——范围校验收敛到 `scope.py`，SQLite 补出了带版本比对的升级通道，参数开始真正接入业务。业务建模（三级责任体系、双日历口径、11 条规则、38 点权限矩阵）依旧是这个项目最强的部分。

**剩下的短板高度集中在三处，且都不难补：**

1. **双库一致性没有工程保障**——索引只写在迁移里，SQLite 一条都没有（P1-1）。这不是"性能问题"，是"同一份代码两个行为"，一旦出问题极难排查。
2. **权限的"写半边"还差最后一块**——大项目四个写接口（P1-2）。
3. **零测试 + lint 不可用**——前三轮修复能这么快、这么准，靠的是人工逐条核对；这个模式不可持续。

按上表前四步走（约 1.5 天），这套系统就具备"交给学校信息中心自己运维"的底子。往后是性能与体验的持续优化，可以按学期节奏推进。
